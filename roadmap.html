Just shipped

M10 — Credential lifecycle (re-enrollment + rotation)

Done

A saved identity that stops authenticating is now a first-class, recoverable condition instead of a generic transport error — at connect time and mid-session.

Shipped

  • IdentityStaleError (a recoverable TransportError): the HTTP transport maps 401/403 to it by default (opt out via stale_statuses); a BLE adapter raises it for a dead bond and the transport propagates it untouched.
  • Identity.last_validated timestamp, stamped on every successful connect (and re-stamped after a mid-session refresh).
  • re_enroll(saved_name, enrollment=...) re-scans, re-enrolls, and atomically overwrites the saved record; connect(saved_name, on_stale=...) recovers a stale bond at open() and retries once.
  • Mid-session auto-refresh — connect(..., on_stale=..., refresh_mid_session=True) wraps command dispatch so an IdentityStaleError raised after connect (e.g. an HTTP token expiring) re-enrolls, rebuilds transports in place, and retries the command exactly once. Off by default, and toggled independently of connect-time on_stale, so a connectivity/auth test harness observes the raw IdentityStaleError instead of silent recovery.

Design detail lives in docs/concepts/lifecycle.md.

M17 — Manifest-wired response interpreters

Done

Every reply is classified by a ResponseInterpreter, and device-specific rules are meant to live in one the SDK author writes — but the manifest couldn’t name one, so the generated SDK always used the family default (HTTP status codes; BLE / loopback: always accepted). A device that reports an error inside a 200 body or a BLE reply was misclassified as ACCEPTED.

Shipped

  • A transport-level interpreter: package.module:Class that the generator import-checks, vendors like a codec, and uses for every operation on that transport; omit it for the family default.
  • A per-operation override: interpreter: in any wiring block (a command’s http: / ble:, an attribute’s read / write / subscribe or ble:, an event’s http: / ble:) replaces the transport’s for that operation — for devices whose endpoints report errors inconsistently.

Design detail lives in docs/concepts/result.md.

M11 — Codegen enrollment helpers

Candidate

Largely superseded by the shipped discover_and_connect() shortcut — most apps never instantiate an *Enrollment adapter at top level anymore; they just hand one to the generated classmethod.

Keep only if…

  • A future survey shows a declarative enrollment: manifest block would meaningfully shrink the adapter constructor itself — login payload shapes, captive-portal flows, multi-step pairing.
  • Original idea: the generator already emits scan_ble() / scan_http() discovery helpers but no enrollment helpers. It could instead read enrollment: {kind: http_login, path: /v1/auth/login} and emit a typed enroll(candidate, saved_name=...) → Identity helper per device.

M12 — Generated-SDK device reference (docs)

Planned

The generated SDK is already a typed, docstringed Python package — standard tools (sphinx-autodoc, pdoc, mkdocstrings, IDE hovers) document its API for free. Kandra should not reinvent that. What no generic tool can see is the manifest-level metadata — wire wiring, capability gates, audiences — and that is the doc worth generating.

Scope

  • Emit an optional device reference at build time (kandra build --docs), reusing the handler + type introspection the generator already does: per operation — dotted id, summary (handler docstring), transports and their wire details (HTTP method/path, BLE channel, expects_response, timeout), request/response schema, required capabilities, idempotent, and audience; plus device-level firmware floor, transports, and discovery.
  • Audience-scoped for free. Generate from the pruned profile, so a --profile partner_woodland reference documents exactly that partner’s surface and leaks nothing internal — the IP-isolation guarantee extended to the docs.
  • Formats: Markdown primary (renders on GitHub, feeds a consumer’s own Sphinx / MkDocs) plus an optional self-contained single-file HTML (inline CSS, zero deps — hand it to a partner).
  • Enable, don’t reinvent, the Python API docs. Document pointing autodoc / pdoc at the package, and optionally have create-sdk drop a ready docs/ stub.
  • Possible follow-on: an OpenAPI-style spec for HTTP devices, or a manifest-digest.json for consumers who want to render their own.

M13 — Serial transport & Classic Bluetooth

Planned

Bluetooth support today is BLE only — bleak speaks GATT, not Classic BR/EDR. Classic is a different stack (inquiry instead of advertisements, SDP profiles instead of GATT characteristics, byte streams instead of write/notify), so it can’t ride the ble family. Most Classic devices worth controlling use the Serial Port Profile (SPP), which the OS exposes as an ordinary serial port once paired — so a serial transport covers them with no Bluetooth-specific code.

Scope

  • A built-in serial transport family over a port path, with message framing left to the device’s codec — covers USB-CDC, UART adapters, and paired Classic SPP devices (/dev/tty.* on macOS, /dev/rfcomm* on Linux).
  • Classic pairing stays an OS step at first; a later enrollment adapter could automate it per platform.
  • Possible follow-on: a direct RFCOMM transport plus a Classic inquiry scanner for when no OS serial port is available (Linux AF_BLUETOOTH sockets; macOS / Windows need platform APIs).
  • Keep the BLE family named ble — renaming it bluetooth would imply Classic support it can’t provide.

M14 — Manifest-declared capability probe

Planned

Operations declare required tags in the manifest (capabilities: [diagnostics]), but the CapabilityProbe that reports a device’s tags is passed only at runtime (discover_capabilities(probe)). Nothing ties the two together, so an SDK author must ship the probe separately and keep it alive through --profile vendoring — and the reference example declares a tag with no probe at all.

Scope

  • A manifest field (e.g. capability_probe: package.module:Class) that the generator resolves, vendors like a handler or codec, and uses as the default, so callers just run await client.discover_capabilities().
  • A real probe for the Pneumatic Bear Poker — e.g. a sim GET /v1/info reporting firmware build flags — so the example shows the full tag → probe → gate loop.
  • Docs: say plainly where the probe lives and how it ships, and stop presenting the example’s bare capabilities: tag as a complete walkthrough.

M15 — Push-updates example (subscribe & events)

Planned

Attribute subscribe and events are fully supported (SSE, opt-in polling, BLE notify) but were removed from the Pneumatic Bear Poker to keep the first example approachable — and its sim only faked a stream anyway. They deserve their own small, honest example.

Scope

  • A bare-bones example device with one subscribable attribute and one event, plus a sim that pushes real changes (current value first, then one frame per actual change) and closes after a short idle timeout so demos and tests terminate.
  • Show mode: sse and opt-in mode: poll side by side, and the async-only facade.
  • Point the Attribute and Event concept pages at it instead of their current illustrative-only snippets.

M16 — Sync (non-async) generated facade

Planned

The generated SDK is async-only, so every caller must write await ... and run an event loop. Plenty of consumers — scripts, notebooks, test rigs, existing sync codebases — explicitly don’t want that. The runtime already has dispatch_sync, and the transport docstring promises a generated SyncClient, but the generator never emits one.

Scope

  • Investigate emitting a sync twin of each device client (e.g. a <Device>Sync alongside the async class) with the same typed methods minus await, generated from the same operation metadata so the two never drift.
  • Decide the loop strategy: asyncio.run per call (simple, but re-opens the transport each time) vs. a long-lived background loop thread owned by the sync client (keeps the connection open, needs clean close() / context-manager semantics).
  • Work out what sync means for streaming surfaces — attribute subscribe and events (blocking iterator, callback, or async-only with a clear error).
  • Make it opt-in or opt-out per build (manifest flag or kandra build --sync) so audiences that don’t need it get a smaller SDK; fix the transport docstring either way.

M18 — Flesh out the Open GoPro example

Planned

The Open GoPro example is deliberately tiny (shutter start / stop over BLE and HTTP). Real cameras report errors inconsistently from one endpoint to the next — exactly the case per-operation interpreters (M17) exist for — but nobody yet knows which endpoints differ.

Scope

  • Open question — ask before starting: which endpoints report errors differently from the rest? Unknown as of M17; find out by testing against a real camera, then name an interpreter: on just those operations.
  • Add a BLE interpreter that reads the TLV status byte, so a refused command comes back REJECTED. Today the codec raises CodecError on a non-zero status, which surfaces as ANOMALOUS.
  • Add more commands and attributes, each checked against the camera.
  • Confirm or drop the discovery server_header_prefix (flagged TODO in the manifest).

Loose ends (small, independent)

Manifest / doc cleanups

  • idempotent / retries command fields. Resolved. Now wired end-to-end: an idempotent command with retries: N is re-sent up to N times after a transient transport failure, and the loader requires idempotent: true for any retries > 0. Wiring this also surfaced and fixed a latent bug — dispatch() was flattening IdentityStaleError into a generic failure, so mid-session recovery now actually fires.
  • Attributes / events interim guard. Resolved. Both primitives are now wired (9b / 9c) and generate working facades; the loader validates their per-transport subscribe wiring. No silent accept-and-ignore, and a shape-valid manifest builds.

Deferred capabilities

  • stream() — bulk byte downloads. Deferred. The Transport protocol reserves a stream() method for long byte transfers (HTTP downloads, BLE bulk transfer), but it is intentionally kept off the shipped protocol until a real feature consumes it — some transports (e.g. BLE for large payloads) may never stream, for product-quality reasons.
  • Structured logging. Deferred decision. The runtime uses stdlib logging with namespaced loggers (kandra.transport.ble, kandra.command.<id>). Revisit whether a richer structured logger earns its non-standard dependency before the runtime grows many call sites.

Non-goals (deliberately out of scope)

Things Kandra will not do

  • No web UI or GUI editor for manifests — CLI plus editor JSON Schema only.
  • No runtime YAML loading in the generated SDK. Once generated, the client package is pure Python; manifests are an authoring-time concept.
  • No plugin marketplace, DSL, or expression language inside YAML — if logic is needed, it goes in a Python handler.
  • No multi-process / RPC server mode — the SDK is a library, not a daemon.
  • No auto-generation of device firmware stubs.
