Just shipped

M10 — Credential lifecycle (re-enrollment + rotation)

Done

A saved identity that stops authenticating is now a first-class, recoverable condition instead of a generic transport error — at connect time and mid-session.

Shipped

  • IdentityStaleError (a recoverable TransportError): the HTTP transport maps 401/403 to it by default (opt out via stale_statuses); a BLE adapter raises it for a dead bond and the transport propagates it untouched.
  • Identity.last_validated timestamp, stamped on every successful connect (and re-stamped after a mid-session refresh).
  • re_enroll(saved_name, enrollment=...) re-scans, re-enrolls, and atomically overwrites the saved record; connect(saved_name, on_stale=...) recovers a stale bond at open() and retries once.
  • Mid-session auto-refresh — connect(..., on_stale=..., refresh_mid_session=True) wraps command dispatch so an IdentityStaleError raised after connect (e.g. an HTTP token expiring) re-enrolls, rebuilds transports in place, and retries the command exactly once. Off by default, and toggled independently of connect-time on_stale, so a connectivity/auth test harness observes the raw IdentityStaleError instead of silent recovery.

Design detail lives in docs/concepts/lifecycle.md.

M11 — Codegen enrollment helpers

Candidate

Largely superseded by the shipped discover_and_connect() shortcut — most apps never instantiate an *Enrollment adapter at top level anymore; they just hand one to the generated classmethod.

Keep only if…

  • A future survey shows a declarative enrollment: manifest block would meaningfully shrink the adapter constructor itself — login payload shapes, captive-portal flows, multi-step pairing.
  • Original idea: the generator already emits scan_ble() / scan_http() discovery helpers but no enrollment helpers. It could instead read enrollment: {kind: http_login, path: /v1/auth/login} and emit a typed enroll(candidate, saved_name=...) → Identity helper per device.

M12 — Generated-SDK device reference (docs)

Planned

The generated SDK is already a typed, docstringed Python package — standard tools (sphinx-autodoc, pdoc, mkdocstrings, IDE hovers) document its API for free. Kandra should not reinvent that. What no generic tool can see is the manifest-level metadata — wire wiring, capability gates, audiences — and that is the doc worth generating.

Scope

  • Emit an optional device reference at build time (kandra build --docs), reusing the handler + type introspection the generator already does: per operation — dotted id, summary (handler docstring), transports and their wire details (HTTP method/path, BLE channel, expects_response, timeout), request/response schema, required capabilities, idempotent, and audience; plus device-level firmware floor, transports, and discovery.
  • Audience-scoped for free. Generate from the pruned profile, so a --profile partner_woodland reference documents exactly that partner’s surface and leaks nothing internal — the IP-isolation guarantee extended to the docs.
  • Formats: Markdown primary (renders on GitHub, feeds a consumer’s own Sphinx / MkDocs) plus an optional self-contained single-file HTML (inline CSS, zero deps — hand it to a partner).
  • Enable, don’t reinvent, the Python API docs. Document pointing autodoc / pdoc at the package, and optionally have create-sdk drop a ready docs/ stub.
  • Possible follow-on: an OpenAPI-style spec for HTTP devices, or a manifest-digest.json for consumers who want to render their own.

Loose ends (small, independent)

Manifest / doc cleanups

  • idempotent / retries command fields. Declared in the manifest model but not wired into the runtime. Either implement them (retry-on-link-drop semantics are non-trivial, especially over BLE) or strike them from the model.
  • Attributes / events interim guard. Resolved. Both primitives are now wired (9b / 9c) and generate working facades; the loader validates their per-transport subscribe wiring. No silent accept-and-ignore, and a shape-valid manifest builds.
